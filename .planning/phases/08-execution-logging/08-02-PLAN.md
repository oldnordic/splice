# Overview

**Goal:** Integrate execution logging into all CLI commands for complete audit trail.

**Context from 08-01:** Execution log schema and builder are ready. This plan adds recording hooks to all operations.

**Key Design Decision:** Logging should be non-blocking. If log recording fails, the operation still succeeds. This ensures:
- Operations don't fail due to log/database issues
- Users can still use splice even if audit log has problems
- Log failures are clearly reported as warnings

## Tasks

### Task 1: Implement recording functions

Create `src/execution/log.rs` with high-level recording functions.

**Files:**
- `src/execution/mod.rs` (new module file, ~50 LOC, re-exports)
- `src/execution/log.rs` (new, ~300 LOC)

**Functions:**
```rust
use crate::execution::ExecutionLog;
use crate::output::OperationResult;

/// Initialize execution log database.
pub fn init_db() -> Result<Connection>;

/// Record operation execution to log.
pub fn record_execution(result: &OperationResult, duration_ms: i64, command_line: Option<String>) -> Result<()>;

/// Record operation with parameters.
pub fn record_execution_with_params(
    result: &OperationResult,
    duration_ms: i64,
    command_line: Option<String>,
    parameters: serde_json::Value,
) -> Result<()>;

/// Record operation failure.
pub fn record_execution_failure(
    execution_id: &str,
    operation_type: &str,
    error: &SpliceError,
    duration_ms: i64,
    command_line: Option<String>,
) -> Result<()>;

/// Get execution log database path.
pub fn db_path() -> PathBuf;

/// Check if execution log is enabled.
pub fn is_enabled() -> bool;
```

**Implementation Details:**
- `db_path()`: Returns `.splice/operations.db`
- `init_db()`: Creates tables if missing, idempotent
- `record_execution()`: Extracts data from OperationResult
- `is_enabled()`: Checks env var `SPLICE_EXECUTION_LOG` (default: true)
- All recording functions use `log::warn!()` on failure (non-blocking)

**Unit tests:** 6 tests
1. `test_init_db_creates_tables` - Database initialization
2. `test_record_execution` - Basic recording
3. `test_record_execution_with_params` - Parameter recording
4. `test_record_execution_failure` - Error recording
5. `test_db_path` - Path resolution
6. `test_is_enabled_default` - Environment variable handling

## Notes

- Recording happens AFTER operation completes (post-execution)
- Duration includes all I/O and validation
- Command line includes original command for reproducibility
- Non-blocking: log failures don't fail the operation
- Operations still log even if they fail (different record type)
